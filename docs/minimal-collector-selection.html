MINIMAL and the invisible selected row

Filter a grid so that a selected row is hidden, then read selected_rows. Every other data return mode still hands you that row. DataReturnMode.MINIMAL does not. Nothing documents the difference, and the version about to ship is the one that introduces it.

Where each collector gets its selections

Both collectors walk the grid once. They just walk different sets of rows, and that single choice is the whole difference.

LegacyCollector · every other mode
api.forEachNode()
↓every row, filtered or not
one node each, carrying isSelected
↓whole node list on the wire
Python filters on isSelected
↓
selected_rows: includes hidden rows
MinimalCollector · MINIMAL
api.forEachNodeAfterFilterAndSort()
↓displayed rows only
push to data, and to selectedRows if selected
↓rows and selection only
Python reads selectedRows verbatim
↓
selected_rows: hidden rows missing

The narrow walk is not an oversight. It is what makes MINIMAL minimal: one pass, no node metadata, no grid state, no column state. Measured at 54.6% smaller than the legacy payload on a 200-row grid, and the gap widens with column count. The selection behavior came along for the ride.

The scenario, concretely

AG Grid does not deselect a row when a filter hides it. Selection and filtering are independent, which is what makes this reachable rather than theoretical:

  1. User ticks three rows.
  2. User types in the quick filter until one of the three is no longer displayed.
  3. The script reads response.selected_rows.

On FILTERED_AND_SORTED, AS_INPUT, FILTERED or CUSTOM, that returns three rows. On MINIMAL it returns two, with nothing to indicate the third was dropped rather than deselected.

Why it matters A "select rows, then act on them" flow silently operates on fewer rows than the user ticked. Delete, export and bulk-edit buttons are exactly this shape, and the failure is invisible: no error, no warning, just a shorter list.

Four ways to settle it

The cheap-versus-correct tension I expected here turned out not to exist. See option A.

A

Match legacy, via getSelectedNodes()

DoesCollect selections from api.getSelectedNodes() instead of inferring them during the display walk, so hidden selected rows come back exactly as in every other mode.
CostI assumed this meant a second full pass over every row, which would have undercut the point of MINIMAL. It does not: getSelectedNodes() is on the AG Grid 35.3 API and returns the selection directly, so the work is proportional to rows selected, not rows present. Payload grows only by the hidden selected rows.
VerdictLow risk Recommended. Same semantics everywhere, nothing to document as an exception, and the cost I was worried about is not real.
B

Keep visible-only, document it as intended

DoesNothing to the code. States in the docstring that MINIMAL reports the selection among displayed rows.
CostZero work, and the semantic is defensible on its own terms: "what the user can currently see selected" is a coherent thing to mean.
VerdictMedium risk The same attribute on the same object means two different things depending on a mode set elsewhere in the call. Documented or not, that is the kind of difference people discover in production.
C

Return both sets

DoesKeeps selected_rows matching legacy and adds something like selected_rows_visible.
CostNew public surface, and duplicate row payloads for anything both selected and displayed, which is most of it. That works against the one thing MINIMAL exists to do.
VerdictMedium risk Solves a problem nobody reported, at the cost of the mode's whole reason for existing.
D

Make it a parameter

DoesAdds a flag so the caller picks which selection semantic they want.
CostMost flexible, most surface. Every reader of the signature now has to understand a distinction they did not ask about, and both paths need tests forever.
VerdictHigh cost A parameter is what you reach for when the right default is genuinely unknowable. Here it is knowable: legacy has behaved one way for years.

What the change looks like

Option A against what is on the branch today.

Now · MinimalCollector.ts
// one pass, display order
api.forEachNodeAfterFilterAndSort((node) => {
  if (node.group) return

  const row = this.stripInternalFields(node.data)
  data.push(row)

  // only rows this walk visited, so a
  // filtered-out selection never arrives
  if (node.isSelected()) {
    selectedRows.push(row)
  }
})

Selection is a by-product of the display walk.

Option A · MinimalCollector.ts
// one pass, display order
api.forEachNodeAfterFilterAndSort((node) => {
  if (node.group) return
  data.push(this.stripInternalFields(node.data))
})

// asked for directly: proportional to the
// selection, not to the number of rows
const selectedRows = api
  .getSelectedNodes()
  .filter((node) => !node.group)
  .map((node) => this.stripInternalFields(node.data))

Selection is asked for on its own terms.

One wrinkle worth knowing first

Read this before choosing A
  • Option A lets a row appear in selected_rows but not in data. MINIMAL's data is the displayed rows, so a hidden selected row is in one and not the other. That looks inconsistent written down.
  • It is what legacy already does. Under FILTERED_AND_SORTED, data is filtered while selections are collected from every node, so the same row can be selected and absent from data today. Option A makes MINIMAL match a wrinkle that already exists rather than inventing one.
  • Group rows need excluding either way. The display walk skips node.group; getSelectedNodes() does not, so it needs the same guard or grouped grids start returning group nodes as if they were data.
  • No test covers this today. Whichever option you pick, it needs one, since the behavior is currently defined only by which API call happens to be in the file.
